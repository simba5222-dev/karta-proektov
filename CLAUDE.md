# Карта проектов (karta)

Живая карта трёх направлений: механизация, отдел продаж, бот MAX.
Показывает состояние, алгоритмы работы каждого проекта и журнал того, что мы делали.

Выходит в двух видах **из одного источника данных**:

| Куда | Адрес | Отметки |
|---|---|---|
| сервер | `http://72.56.25.105/karta/`, nginx, basic-авторизация, пользователь `karta` | localStorage браузера |
| claude.ai | `https://claude.ai/artifact/NzvPbLZJXbY91WyTAEFYH7` | общая база, доступна агенту на чтение |

Содержание у них одинаковое. Расходиться они не должны — если разошлись,
**источник правды этот репозиторий**, надо пересобрать и выложить обе.

## Как устроено

| Файл | Что это |
|---|---|
| `data.json` | **всё содержание**: блокеры, проекты, алгоритмы, задачи, журнал |
| `style.css` | вёрстка, светлая и тёмная темы |
| `build.py` | сборка обоих видов. Только stdlib, зависимостей нет |
| `deploy.sh` | собрать серверный вид и скопировать в `/var/www/karta/` |
| `index.html`, `artifact.html` | результаты сборки, в git не хранятся |

    python3 build.py              собрать серверный вид
    python3 build.py --artifact   собрать вид для claude.ai
    ./deploy.sh                   собрать и выложить на сервер

Правится **только `data.json`**. Руками собранные файлы не трогать — перезапишутся.

Тексты в JSON — это готовый HTML внутри абзаца: можно писать `<code>`, `<b>`, `<em>`.
Экранирования нет намеренно, файл пишем мы сами.

## Главное правило

**Эта карта — журнал работы, а не снимок состояния.** Владелец просил, чтобы на ней
отражалось всё: обсуждения, планы, выполненные работы, принятые решения.

В конце каждого сеанса дописывать в `journal` записи за сегодняшнюю дату. Типы:

- `решение` — что решили и **обязательно `why`**, иначе через месяц непонятно, почему так
- `сделано` — что реально сделано
- `выяснено` — что обнаружили: блокер, особенность среды, ложная гипотеза
- `открыто` — вопрос, который завис и ждёт ответа

Поле `who` заполняется, когда решение принял владелец, а не агент.
Новые дни добавляются в любое место массива — сортировка по дате делается при сборке.

После правки выложить **обе** версии: `./deploy.sh` и публикация `artifact.html`
инструментом Artifact с `url` существующего артефакта.

## Тонкости, которые легко сломать

- **Заголовок артефакта неизменен.** `title_artifact` в `data.json` — по нему артефакт
  узнают в галерее claude.ai. Менять нельзя, читается как другая страница
- **Артефакт не оборачивать в документ.** claude.ai добавляет свои `<html>`, `<head>`
  и `<body>` сам; в `artifact.html` только `<title>`, `<style>` и содержимое
- **Три состояния темы.** У артефакта тема бывает системной и двух явно выбранных.
  Простого `prefers-color-scheme` мало — `build.py` раскладывает токены тёмной темы
  в защищённые ветки сам, из того же `style.css`. Регулярка ищет блок
  `@media (prefers-color-scheme:dark)` — если переписать его в `style.css` иначе,
  сборка артефакта упадёт с понятной ошибкой
- `deploy.sh` вызывает `sudo cp`, поэтому запускать под `agent` (у него sudo без
  пароля). Под `claude` sudo спросит пароль

## Чего не делать

- **Не печатать на странице секреты.** Серверная версия отдаётся по http, без
  шифрования: ни паролей, ни токенов, ни реквизитов. Про дефолтный пароль механика
  написано, что он дефолтный, но само значение не приводится — так и оставить
- Не хранить собранные html в git — они генерируются
- Не заводить зависимости: `build.py` должен работать системным python3 без venv
